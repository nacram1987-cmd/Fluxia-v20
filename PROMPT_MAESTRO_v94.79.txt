## NUEVAS LEYES v94.79 (SUPABASE SYNC CRÍTICA)

### PRINCIPIO #22: SINCRONIZACIÓN AUTOMÁTICA A SUPABASE ES OBLIGATORIA
**La fuente del bug garrafal v94.78:** Los datos se guardaban en localStorage pero NO subían a Supabase automáticamente.
Esto causaba pérdida de datos al reinstalar PWA y pérdida de confianza crítica.

**Implementación v94.79:**
```javascript
// 1. Listeners automáticos en localStorage
window.addEventListener('storage', e => {
  if (e.key.startsWith('planRescate_') || e.key.startsWith('fluxia_')) {
    Almacen.flush(); // SINCRONIZAR INMEDIATAMENTE
  }
});

// 2. Intercept de setItem/removeItem
Storage.prototype.setItem = function(key, value) {
  originalSetItem.apply(this, arguments);
  if (key.startsWith('planRescate_') || key.startsWith('fluxia_')) {
    programarFlushAutomatico(key);
  }
};

// 3. Retry automático con exponential backoff (1s, 2s, 4s, 8s, 16s)
// Si falla, reintenta hasta 5 veces

// 4. Toast visual en top-right
// "✓ Sincronizado" (verde) | "⟳ Sincronizando..." (gris) | "⚠ Error" (naranja) | "✗ Sin conexión" (rojo)

// 5. Synchronización entre tabs (localStorage event funciona entre pestañas)

// 6. Flush al cerrar app (beforeunload → vaciar + flush)
```

**Verificación:**
```bash
# En Console del navegador:

[Almacén v94.79] Storage event detectado: planRescate_movimientos
[Almacén v94.79] Ejecutando flush automático
[Almacén v94.79] Status: ok
✓ Los datos suben EN TIEMPO REAL
```

**Cuando algo FALLA:**
- No espera: reintenta automáticamente
- Usuario ve "⚠ Error de sync" en top-right
- Reintenta en 1s, 2s, 4s, 8s, 16s (max 5 intentos)
- Si falla permanentemente: "✗ Sin conexión"

## LEYES v94.77 (vigentes + sin cambios)

### PRINCIPIO #16: index.html DEBE SER IDÉNTICO a index_fluxia_vX.X_LAB.html
- index.html es lo que sirve la app. Debe ser byte-to-byte igual.
- Verificación: `cmp index.html index_fluxia_vX.X_LAB.html`
- Antes de entregar: grep de versiones sobre AMBOS archivos

### PRINCIPIO #17: TODA decisión del usuario vive en el Almacén (nube), no solo en localStorage
- iOS borra localStorage cuando quitas app de pantalla de inicio
- FluxiaEspejo copia decisiones al Almacén
- Toda clave nueva se añade a expresión RE de FluxiaEspejo

### PRINCIPIO #18: LOS REGISTROS QUE SOLO CRECEN SE FUSIONAN POR ID
- Aportaciones y usos de huchas llevan id
- Si local y nube difieren: se unen por id (nunca gana una sola versión)
- Función: `_fusionarHuchas(k, lv, rv, localGana)`

### PRINCIPIO #19: `window.Almacen` NO EXISTE
- `const Almacen` es un const global, no cuelga de window
- Usar: `typeof Almacen !== 'undefined'`
- Hay 15 guardas heredadas `window.Almacen && …` sin ejecutar (auditar una por una)

### PRINCIPIO #20: ESTILOS: un `style.color` en línea NO vence a `!important`
- Para cambiar un color: alternar una CLASE con regla más específica + `!important`
- Disponible negativo: `var(--wine-dark)` `#8B3A3A`
- Selector de meses: oro `#8B6914→#6B5312` con texto blanco, contraste ≥6:1

### PRINCIPIO #21: MOVIMIENTOS PENDIENTES (PDNG) RESTAN DEL DISPONIBLE
- Enable Banking devuelve `status:"BOOK"` (contabilizadas) y `status:"PDNG"` (pendientes)
- Edge Function pide ambos: `for status of ["BOOK", "PDNG"]`
- El cliente marca `pendiente: true` si `t.status !== "BOOK"`
- Disponible ya incluye PDNG: los fondos están bloqueados YA

## PRINCIPIOS DE NEGOCIO (Intactos desde v94.66)

### Contexto: Fluxia es "tu plan de dinero mes a mes"
- **Usuarios**: Personas que quieren presupuestar mes a mes (no día a día)
- **Problema**: Ignorancia de cuánto pueden gastar sin quebrar provisiones
- **Solución**: Calcular cada mes qué está disponible DESPUÉS de pagar provisiones

### Contrato del usuario
1. Digamos ingresos esperados
2. Digamos gastos fijos mensuales (alquiler, seguros, etc)
3. Digamos provisiones mensuales (hucha para reparaciones, vacaciones, etc)
4. Fluxia calcula: disponible = ingresos - fijos - provisiones
5. Gastos clasificados. Al final del mes, Fluxia dice si quedó "en verde" o "en rojo"

### Reglas de negocio: No negociables
1. **Las provisiones no son gastos**: son dinero que apartas hoy para gastar después
2. **El "Disponible" es lo más importante**: el usuario quiere saber qué puede gastar HOY
3. **Los meses son fronteras duras**: cambiar de mes = resetear gasto total (pero las provisiones se arrastran)
4. **iOS borra datos**: todo debe poder restaurarse desde la nube
5. **Gastos del banco importan**: si el banco no vio un gasto, no existió (Enable Banking)
